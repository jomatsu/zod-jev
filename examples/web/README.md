# デモ web アプリ（普通のフォーム + 裏で JEV）

**利用者向けのページは、ごく普通のレビュー投稿フォームです。** JEV の存在・確率・条件 ID は一切出しません。
裏側で Zod が「形」を、TypeSafe JEV が「意味」を判定し、その結果を普通のプロダクト状態に写像します。

| 画面 | 役割 |
| --- | --- |
| `/` | 商品レビューの投稿フォーム（利用者向け） |
| `/ops` | 投稿の裏側の記録（運用者向け。確率・送信内容・トークンが見える） |

```sh
# 実 API（TYPESAFE_API_KEY か .env が必要。1 判定で約 $0.00005）
npx tsx examples/web/server.ts

# 偽の判定で試す（鍵不要・課金なし）
npx tsx examples/web/server.ts --fake

# 導入の途中を再現する
npx tsx examples/web/server.ts --mode=shadow   # 判定はするが挙動は変えない（記録のみ）
npx tsx examples/web/server.ts --mode=off      # JEV を呼ばない（キルスイッチ。鍵が無くても起動できる）
```

→ 利用者向け http://localhost:5178/ ・運用画面 http://localhost:5178/ops

## 裏側の流れ

```
フォーム送信
  │
  ├─ (1) Zod: 形（必須・文字数・メール形式）          同期。ここで落ちたら JEV は呼ばない
  │
  ├─ (2) JEV: 意味（条件を 1 リクエストにまとめて送る）  非同期
  │        no_personal_information / no_promotion / rating_matches_body / body_has_specifics
  │
  └─ (3) プロダクト状態への写像（アプリ側のポリシー）
           rejected              → 入力エラーとして直してもらう（インライン表示）
           uncertain/unavailable → 受け付けて「審査中」（利用者には普通の案内文だけ）
           合格                   → 「掲載待ち」
```

利用者に見えるもの / 見えないもの:

| | 利用者（`/`） | 運用者（`/ops`） |
| --- | --- | --- |
| 形式エラー | 「ニックネームを入力してください」 | 同左 |
| 意味の違反 | 「個人情報は入力しないでください」（普通のエラー） | どの条件が何 % で落ちたか、閾値つきで見える |
| 判断できなかった | **何も見えない**（「確認させていただく場合があります」だけ） | `uncertain` / `unavailable` と確率が見える |
| JEV の送受信内容 | 見えない | `state` / `questions` / `answers` / トークン / レイテンシ |

## 構成

| ファイル | 役割 |
| --- | --- |
| `server.ts` | `node:http` のサーバー。`POST /api/reviews`、`GET /api/reviews`、`GET /api/meta`、静的配信 |
| `review.ts` | ドメイン層。スキーマ・条件・プロダクト状態への写像・記録（HTTP からもテストからも同じ経路） |
| `fake.ts` | `--fake` 用の偽 JEV と、デモ用サンプル投稿 |
| `public/index.html` `app.js` | 利用者向けフォーム（フレームワークなし） |
| `public/ops.html` `ops.js` | 運用画面（3 秒ごとに自動更新） |

## 設計上のポイント

- **API キーはサーバー側にだけ置く。** 公式 SDK もブラウザ実行を拒否するため、JEV の呼び出しは必ずサーバーで行います。
- **利用者に AI を見せない。** 判定結果は「掲載待ち / 審査中 / 差し戻し」という普通の状態に写像し、文言も普通のフォームのものにしています。
- **`uncertain` をエラーにしない。** 判断できなかっただけで入力が悪いわけではないので、受け付けて「審査中」にします（可用性優先）。この判断がアプリ側にあることが、ライブラリを 2 段構えで使う理由です。
- **送受信の記録はリクエストごとの非同期コンテキスト**（`AsyncLocalStorage`）に閉じ込めています。デモで中身を見せるための仕掛けで、本番では `onResponse` でメトリクスを送るだけにして、利用者の入力を全量保存しないでください。
- `--fake` は入力の特徴から確率を決めるだけの偽物です。UI と分岐の確認用で、JEV の精度とは関係ありません。

## 制限

- サーバーレンダリング＋メモリ上の記録だけの最小構成です。DB・認証・モデレーション画面の操作（承認/却下）・レート制限はありません。
- 記録は最大 100 件（`limit`）で、プロセスを再起動すると消えます。
