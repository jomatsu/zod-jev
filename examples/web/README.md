# デモ web アプリ（普通の出品画面 + 裏で Jev）

**利用者向けのページは、一般的なフリマアプリの出品画面です。** Jev の存在・確率・条件 ID は一切表示しません。
出品ボタンの裏で Zod が「形」を、TypeSafe Jev が「意味」を判定し、その結果を通常のプロダクト状態に写像します。

| 画面 | 役割 |
| --- | --- |
| `/` | 出品画面（利用者向け）。写真・カテゴリー・状態・配送料・手数料計算まで、よくある形 |
| `/ops` | 判定の裏側（開発者向け）。条件ごとの確率・閾値・送信内容・トークンが見える |

公開: **https://zod-jev.jomatsu.me/**（`/ops` は開発者向け）

```sh
# ローカルの Node サーバー（実 API）
npm run demo:web

# 偽の判定で試す（鍵不要・課金なし）
npm run demo:web:fake

# Cloudflare Workers としてローカル実行（.dev.vars にキーを置く）
npm run dev:web        # → http://localhost:8788

# デプロイ / Secret の登録
npm run deploy:web
npx wrangler secret put TYPESAFE_API_KEY --config examples/web/wrangler.jsonc
```

## 裏側の流れ

判定が実行される契機は **2 つ**あります。

```
(A) フォーカスを外したとき（途中チェック）        (B) 「出品する」を押したとき
  │                                              │
  ├─ (1) Zod: 入力済みのフィールドだけ検証          ├─ (1) Zod: 全部の必須項目を検証
  │      足りない項目があれば Jev は呼ばない        │
  │                                              │
  ├─ (2) Jev: 必要なフィールドが揃った条件だけを     ├─ (2) Jev: 6 条件を 1 リクエストで全部
  │      1 リクエストにまとめて送る（0〜6 条件）     │       0.2〜0.5 秒
  │                                              │
  └─ (3) 結果はその場で返す（保存しない）           └─ (3) 保存 + プロダクト状態への写像
         該当項目の下に理由、デモパネルに確率             rejected → 出品不可（該当項目の下に理由）
        「出品するまで結果は確定しません」                uncertain/unavailable → 審査中
                                                        合格 → 出品が完了しました（公開中）
```

途中チェックで判定する条件は、**その条件に必要なフィールドが入力されているものだけ**です（未入力の項目について不要な判定を行わせないためです）。

| 条件 | 途中チェックで必要な入力 |
| --- | --- |
| `no_prohibited_items` | 商品名 + 説明 |
| `no_contact_or_external` | 説明 |
| `category_matches_item` | カテゴリー + 商品名 + 説明 |
| `condition_matches_description` | 商品の状態 + 説明 |
| `price_is_plausible` | 価格 + 商品名 + 説明 |
| `description_is_sufficient` | 説明 |

リクエストの抑制: フォーカスが移動するたびに実行されないよう、**400ms のデバウンス**と**同一入力時の再判定防止**（内容の比較）を実装しています。`off` モードでは Jev を呼び出しません。

利用者に見えるもの / 見えないもの:

| | 利用者（`/`） | 開発者（`/ops`） |
| --- | --- | --- |
| 形式エラー | 「商品名を入力してください」（フォーカスを外した時点で出る） | 同左 |
| 意味の違反 | 「連絡先や外部サイトの記載はできません」（普通のエラー） | どの条件が何 % で落ちたか、閾値つきで見える |
| 判断できなかった | **何も見えない**（「審査が終わり次第公開されます」だけ） | `uncertain` / `unavailable` と確率が見える |
| Jev の送受信内容 | 見えない | `state` / `questions` / `answers` / トークン / レイテンシ |

## 判定に使っている条件

| 条件 ID | 成立していてほしいこと | 閾値 |
| --- | --- | --- |
| `no_prohibited_items` | 出品禁止物（医薬品、模倣品、金券、生き物、武器、他人の個人情報…）を示していない | 0.90 |
| `no_contact_or_external` | 説明に電話番号・メール・SNS ID・外部 URL が含まれていない | 0.90 |
| `category_matches_item` | 選択カテゴリーが商品名と説明の内容と一致している | 0.90 |
| `condition_matches_description` | 選択した「商品の状態」が説明の記載と矛盾していない | 0.85 |
| `price_is_plausible` | 価格が内容に対して極端に相場から外れていない（`context.price_guide` を参照） | 0.90 |
| `description_is_sufficient` | 状態・型番・付属品など、購入判断に必要な情報が書かれている | 0.65 |

## デモ操作パネル（メタUI）

フリマ風の画面には**デモ用の UI を一切混ぜていません**。サンプルの入力や裏側の判定結果は、**デモ操作パネル**（暗い配色・`DEMO` バッジ・破線の区切り）に配置しています。デスクトップでは画面の右側に固定し、狭い画面では**下から出るシート**に切り替わります。パネル自体にも「このパネルはアプリの一部ではありません」と明記しています。

パネルの中身:

1. **例を入れる（1クリック）** — 下の表に示す 7 件です。クリックするとフリマ風のフォームに内容が入力されます。
2. **直前の出品の判定（裏側）** — 出品を実行するたびに、6 条件すべての確率・閾値・合否（✓/✗/▲）および model / questions / tokens / latency が表示されます。`→ 出品不可（理由は該当項目の下に出る）` のように、プロダクト状態への写像結果も確認できます。
3. **詳しく見る** — `/ops` へのリンクと、現在の動作環境（実 API または `--fake`）の表示です。

幅の狭い画面（1180px 以下）では、パネルが画面下部のブロックに配置されます。

| 下書き | 何が起きるか |
| --- | --- |
| 良い出品（そのまま出品できる） | 公開中 |
| 説明に連絡先を書いた | 出品不可（`no_contact_or_external`） |
| 出品できない物（市販薬） | 出品不可（`no_prohibited_items`） |
| カテゴリーが違う | 出品不可（`category_matches_item`） |
| 状態と説明が矛盾している | 出品不可（`condition_matches_description`） |
| 価格が相場から外れている | 出品不可（`price_is_plausible`） |
| 説明が薄い | 出品不可または審査中（`description_is_sufficient`） |

## 実測（2026-09-17 / `jev-1.13.0`）

| 出品 | HTTP | 結果 | 実際の確率 |
| --- | --- | --- | --- |
| 良い出品（カメラ、説明が具体的） | 201 | 公開中 | issue なし（`tokens=2030`, 448ms） |
| 説明に電話番号とメール | 422 | 出品不可 | `no_contact_or_external=0.02` |
| 市販薬のまとめ売り | 422 | 出品不可 | `no_prohibited_items=0.02`, `description_is_sufficient=0.30` |
| 「カメラです。よろしくお願いします。」 | 422 | 出品不可 | `description_is_sufficient=0.05` |
| 傷だらけなのに「目立った傷や汚れなし」 | 422 | 出品不可 | `condition_matches_description=0.05` |

1 出品あたり input 約 1,900〜2,050 tokens（6 条件 + 出品ガイドライン + 相場の目安）＝ **約 $0.00008**、レイテンシ 160〜470ms です。条件を増やしても 1 リクエストに集約して送信するため、所要時間はほとんど変わりません。

閾値も実測値に基づいて調整しています（コード内にもコメントを記載しています）。

- `description_is_sufficient`: 詳しい説明では 0.9 以上、短い説明では 0.1 以下となったため、0.85 → **0.65** に変更しました。
- `condition_matches_description`: 説明に傷の言及があると、状態と矛盾していなくても 0.86 程度まで低下することがあったため、0.90 → **0.85** に変更しました。

## 構成

| ファイル | 役割 |
| --- | --- |
| `listing.ts` | ドメイン層。スキーマ・6 条件・プロダクト状態への写像・記録（HTTP からもテストからも同じ経路） |
| `server.ts` | ローカル用の `node:http` サーバー（`--fake` / `--mode=off\|shadow` 対応） |
| `worker.ts` | Cloudflare Workers 版。静的は Workers Assets、記録は Durable Object |
| `wrangler.jsonc` | Workers の設定（nodejs_compat / Assets / Durable Object / カスタムドメイン） |
| `fake.ts` | `--fake` 用の偽 Jev と、`/ops` のデモ用サンプル出品 |
| `public/` | 画面（フレームワークなし）。`index.html`+`app.js` が出品画面、`ops.html`+`ops.js` が裏側 |

### モバイル（幅 1180px 以下）

- デモ操作パネルは**画面下から出るシート**になります。閉じているときはバー（高さ 52px）だけが見え、
  タップで開閉します。バーには直前の判定の要約（例: `出品不可・指摘 4 件`）が出るので、
  シートを開かなくても結果が分かります（違反があると色が変わります）
- 「出品する」を押すとシートは自動で閉じます（判定はバーに出ます）。入力例を選んだときも閉じます
- フォームは1列になり、入力欄の文字サイズは iOS の自動ズームを避けるため 16px にします
- `/ops` の条件一覧などの表は横スクロールになります

## 設計上のポイント

- **API キーはサーバー側にのみ配置します。** 公式 SDK もブラウザ実行を拒否するため、Jev の呼び出しは必ずサーバーで行います。
- **利用者に AI の存在を意識させません。** 判定結果は「公開中 / 審査中 / 出品不可」という通常のプロダクト状態に写像し、文言も一般的なフォームと同様の表現にしています。
- **`uncertain` をエラーとして扱いません。** 判断できなかっただけで入力が不正なわけではないため、受け付けて「審査中」にします（可用性優先）。この判断をアプリケーション側で柔軟に決定できることが、本ライブラリを 2 段階で構成している理由です。
- **写真は state に含めません**（`SemanticOptions.toJSON`）。判定に不要な情報を送信せずに済みます。
- **初期表示は「前回の下書き」** として用意しています（実際のアプリケーションでも下書きが保存される挙動を再現しています）。デモ用のサンプルはサーバーの `/api/meta`（`fake.ts` の `samples`）が唯一の定義であり、`/ops` のデモボタンと同じデータを使用しています。
- **裏側の判定をデモ操作パネルに返す**ため、`POST /api/listings` の応答に `demo`（条件ごとの確率・送信内容）を含めています。**本番運用の API ではこれらの情報を返却しないでください**（`server.ts` / `worker.ts` にコメントを記載しています）。
- 送受信の記録はリクエストごとの非同期コンテキスト（`AsyncLocalStorage`）に分離しています。これはデモで詳細を表示するための仕組みです。本番環境では `onResponse` でメトリクスを送信する構成にとどめ、利用者の入力を全量保存しないでください。
- `--fake` は入力の特徴から確率を算出する擬似的な実装です。画面 UI と条件分岐の確認用であり、実際の Jev の精度とは関係ありません。

## Cloudflare Workers 固有のメモ（実測で踏んだこと）

- **受付記録は isolate ごとのメモリに配置してはいけません。** 当初はモジュールスコープの配列で保持していましたが、リクエストが別の isolate にルーティングされるため、3 件出品しても `/ops` に 1 件しか表示されないことがありました。現在は Durable Object に永続化して解決しています。
- `durable_objects` のバインディングは**名前空間**であり、`.fetch` は直接呼び出せません。`get(idFromName("listings"))` でスタブを取得して呼び出します（RPC は使用せず HTTP 通信のまま処理しています）。
- ローカルの `wrangler dev` では Secret が使用されないため、`examples/web/.dev.vars` に `TYPESAFE_API_KEY` を配置します（gitignore に追加済みです）。
- API キーがない状態でもデプロイできるよう、`REVIEW_MODE=off` のときは Jev のクライアントを生成しない設計にしています（キルスイッチ）。また `FAKE_JEV=1` を指定すれば、擬似的な判定によって課金なしで動作を確認できます。

> 記録には利用者の入力内容を含みます（`state` / `questions` / `answers`）。デモとして可視化するための全量保存ですので、本番環境では保持する項目を絞るか、`onResponse` によるメトリクス記録のみに限定してください。

## 制限

- フォーカスを外すたびに 1 リクエスト（約 $0.00008）が実行されます。デバウンスと重複判定によってリクエスト数を抑制していますが、本番環境では「入力が揃った最初の 1 回だけ検証する」「一定時間キャッシュする」などの制御を導入してください。
- 画像アップロードは UI 表示のみのダミー実装です（判定にも使用しません）。認証・DB・検索・購入フローは実装していません。
- 記録件数は最大 100 件です（`limit` / `STORE_LIMIT`）。Node サーバー版では再起動時に消失しますが、Workers 版では Durable Object に保持されます。
- `/ops` には認証を設けていません（公開デモ用途のため）。本番運用時には必ずアクセスを保護してください。
